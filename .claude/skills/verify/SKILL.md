# Verifying Cellar Floor changes

## Build and launch

```bash
cd client && npm run build && cd ..   # tsc + vite build into client/dist
go run ./cmd/cellarfloor              # serves client/dist and /ws on :8080, run in background
```

The server loads the persisted world from `world.json` (log line: "loaded world at tick N"). Use `-fresh` for a new world, `-seed` to control generation. Check readiness with `curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/`.

## Inspecting sim state (prefer this over pixel-scanning)

Read-only JSON endpoints on the running server:

```bash
curl -s localhost:8080/api/state                          # tick, timeScale, pops, entity count
curl -s 'localhost:8080/api/entities?type=dwarf&alive=true'   # EntityView list, filters combinable
curl -s 'localhost:8080/api/entities?type=torch'              # type= matches any entity type, structures too (campfire, torch, dwarf)
curl -s localhost:8080/api/entities/1481                  # one entity; 404 unknown id, 400 non-numeric
curl -s -X POST 'localhost:8080/api/advance?ticks=200000' # fast-forward ~a day; broadcasts a snapshot
```

Entity JSON matches the ws EntityView shape (`id`, `s`, `x`, `y`, `dead`, `full`, `action`, `home`, `res`). Use these to find a creature's tile before clicking it (tile * 12 canvas px), to confirm liveness (tick advances), or to watch populations. Pixel-scanning is only needed to verify what is actually drawn.

## Driving the UI

The Claude Chrome extension may not be connected; headless Playwright against installed Chrome works:

```bash
cd <scratchpad> && PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm install playwright
# then: chromium.launch({ channel: 'chrome', headless: true })
```

The whole map is one `<canvas>` (no DOM per entity). Prefer finding entities via `/api/entities` and converting tile to canvas px (tile * 12); pixel-scanning via `getImageData` also works with data-driven colors. Terrain colors come from `data/terrain.toml` (grass `#3d5a36`, dirt `#6b5537`, water `#2b4a63`, rock `#3a3a3a`, floor `#26221e`, soft rock `#575049`, mold `#7a8a4d`); the snapshot ships this table as `terrainTypes` and the client renders each cell from it. Soft rock (`#575049`) is a faster-mined vein (7200 hit points, ~1h, vs 28800 / ~4h for plain rock in `data/terrain.toml`) that worldgen grows as connected blobs; it only appears in newly generated worlds. Mold (`#7a8a4d`, index 6) is a very weak block (6 hit points, ~3 seconds to mine) that worldgen lays as a full crust ring around the clearing (every rock cell 8-adjacent to the clearing's dirt becomes mold at gen time, `crust`/`crust_chance` in `data/gen.toml`), so day-one dwarves chew through it fast. Gold veins (`gold_vein`, index 7, `#6e5a2e`, 14400 hp, `chip_gold = 15`, `glints = true`) generate as small blobs scattered through the deep rock and SPARKLE through the fog client-side (a twinkling 2px `#ffd75e` dot drawn above the veil), so they are visible mid-term goals before they are lit or reachable. The clearing dirt reaches tile radius ~12 from the center (32,32) and the mold crust ring sits just outside it at radius ~12-13, beyond the campfire's radius-8 light, so the crust starts DARK and un-mineable; a torch (light radius 5) placed on a passable dirt tile within 5 of a crust cell lights it and gives a spawned dwarf its first mineable face (this is the day-one loop: spawn, torch the crust, watch the dwarf dig). Mold also has a spread rule (`spread_minutes = 20`): each mold block has a small per-tick chance to convert one random 8-neighbor that is passable, UNLIT, and fauna-free into mold, so mold creeps into dark passable space and torch/campfire light suppresses it. The crust and spread only appear in worlds generated after these config changes (a server restart plus a world reset), never in an old save loaded from `world.json`. Entity and structure colors come from `data/entities.toml` (dwarf `#d9a066`, mushroom `#c4b5d9`; structures: campfire `#e25822`, torch `#ffb347`; mining bar track `#1a1815`, fill `#ffb347`; dead `#443c38`, selection box `#ffd75e`). Unlit cells are covered by a darkness veil (`rgba(0, 0, 0, 0.75)` drawn over the terrain), so only cells inside a light circle read at full brightness; pixel-scan lit cells (near a campfire or torch) when checking terrain colors. Tiles are 12 canvas px; the canvas is CSS-scaled, so convert with `canvas.getBoundingClientRect()` before `page.mouse.click`.

Useful DOM handles: `#popup` (entity inspector popup inside `#map`), `#pops` (population labels), `#events` (event feed with tick numbers), `#debugmenu` (the Tab-toggled debug menu holding `#timescale` speed buttons pause/1x/8x/64x, the reset button, `#debug-gold10`/`#debug-gold100`, `#debug-level` "complete level", and `#debug-claims` +/- rows; press Tab via page.keyboard first, or a three-finger tap on touch; speed and debug intents are open to everyone, while reset and POST /api/advance still require CELLAR_ADMIN_TOKEN (unset = open) via localStorage "admin" / the admin query param), `#levelbox` (the colony level bar: `#levellabel` "Lv N" + `#levelfill`), `#claimcard` (the pending-upgrade card: `#claimtext`, `#claimmore`, `#claim-btn`), `#recap` (the welcome-back toast).

## Colony levels and claimed upgrades

`data/upgrades.toml` is now a level CURVE plus a random draw POOL (a NEW REQUIRED data file: a data dir missing it fails to boot; refresh every scratch/fixture dir from `data/`). Two scalars define the curve: `level_base` (mined gold for the first level) and `level_growth` (each level costs `level_growth`x the last, rounded up). Each `[[upgrade]]` is a pool entry: `name`, `kind` (`damage`, `luck`, `weapon`, `beam`, or `missile`), `amount`, `max` (0 = unlimited), and weapons/beams/missiles add `color`/`radius`/`period_ms`. Cumulative mined gold (`GoldMined`, lifetime, never spent) drives levels. ALL gold pays instantly at the rock face — per-swing chips, with golden-strike crits as the jackpot layer; the ore-hauling/market-deposit loop is GONE (no `carry_capacity`, no `ore` on the wire, no "ore"/"sold" events, no "hauling ore"/"selling" actions). The market structure still exists (entity type with `market = true`, spawned by worldgen near the campfire and auto-spawned into old saves on load, rendered as the 0x72 golden chest) but is currently decorative. Claimed `speed` upgrades (Swift Boots, +25%/claim) multiply every walk via `World.SpeedFactor`. The ws snapshot and every tick ship `level`, `goldMined`, `prevLevelGold`, `nextLevelGold`, `pendingLevels` (unclaimed level count), `offer` (the current up-to-3 choices), `claims` (name->count), and the whole `upgrades` table. `prevLevelGold`/`nextLevelGold` ride the wire so the client never hardcodes the curve. Each level reached with any eligible entry (`max` 0 or claims below `max`) increments `pendingLevels` and fires a "level" event; the server keeps ONE offer rolled at a time (up to 3 distinct eligible names, world-RNG deterministic). Legacy saves with the old `pending` name queue migrate on load: each queued name becomes one pending level.

Level bar `#levelbox` (`#levellabel` "Lv N" + `#levelfill`) fills from `(goldMined - prevLevelGold) / (nextLevelGold - prevLevelGold)`. Claim card `#claimcard` is hidden unless an offer exists; `#claimtext` reads "Level N reached: choose an upgrade", `#offerbox` holds one button per offered upgrade (name plus a kind-derived effect line, disabled without a living dwarf), `#claimmore` reads "+K more levels waiting" when levels are stacked, and clicking an option sends `{type:"claim", player, name}` (errors: "nothing to claim", "not on offer"). Claiming consumes one pending level and immediately rolls the next offer until the stack drains.

CRITICAL - pending draws are INERT until claimed. `World.ClaimOffer` bumps `claims[name]` for the picked option only; only CLAIMED upgrades feed `World.MineBonus` (summed `damage`+`weapon` amount, boosts every miner's per-tick damage) and `World.LuckBonus` (summed `luck` amount, percentage points added to the golden-strike chance: `World.CritChance()` = `sim.crit_chance` + LuckBonus/100). Ground truth is the ws `mining` map at 1x (one tick message per sim tick): a mined cell's damage climbs by `mine_damage + MineBonus` per tick - +1/tick while a draw sits UNCLAIMED (claims stay empty), then +2/tick after claiming a `damage`/`weapon` amount-1 upgrade (mold's 6 hit points then break in 3 ticks instead of 6). A claimed Lucky Veins raises golden-strike odds (+2pp per claim). Higher timescales batch N ticks per broadcast, so sample deltas at 1x. Claiming is FIFO: the card advances to the next oldest. Everything persists in the save; a fresh world starts at level 0 with empty pending/claims. The recap toast appends " N levels await your choice!" when pendingLevels is non-zero on reconnect.

Beams and missiles are NON-AOE damage: claimed `beam` (Lance, white `#ffffff`, amount 3) and `missile` (Seeker, pale blue `#8fd3ff`, amount 2, a dot that flies a curved elongating trail from the dwarf's back around its side into the face, alternating sides per shot) upgrades add `World.BeamBonus` damage ONLY to the miner's chosen target face (`mt` on the EntityView), not to the other swept neighbors, so the target's per-tick delta runs `mine_damage + MineBonus + BeamBonus` while neighbors get `mine_damage + MineBonus`. Client-side the beam is a thin line (radius = length in px) that aims parked behind the dwarf's back for 55% of `period_ms`, flies through the target face until 80%, spawns debris and a shake on arrival, then vanishes until the next cycle.

Weapon orbits: a claimed `weapon` upgrade (Chisel `#e8d44d`, Hammer `#b87333`) draws an EXTRA tool sprite orbiting each MINING dwarf (`action=="mining"`) at that upgrade's `radius`/`period_ms`, alongside the base pick orbit (`#cfd6dd`, radius 14). Orbits render only while a dwarf is mining, and once MineBonus is high mold breaks in ~2 ticks so bursts are brief - pause (timescale 0) to freeze a miner mid-swing before screenshotting.

The economy is a torch-driven loop: mold only forms in DARK passable cells, and a dwarf can only mine LIT mineable faces, so each torch lights a finite mold pocket that a food-led dwarf chews through, paying chips per swing plus break-time jackpots straight to colony gold. Warning for e2e: mine targets come ONLY from food-digging (a mushroom buried past the face); they persist until mined out or unlit. Boost damage via debug claims to make any face breakable quickly. Also note pathfinding is light-blind: a shortest path through unlit cells triggers the flee-the-dark loop (a known, pre-existing quirk). Sustained leveling means re-torching freshly-spread dark mold; to fast-forward, place torches on dense rock-free mold pockets then `POST /api/advance`.

## The recap toast (returning players)

The world tracks lifetime counters (`BlocksMined`, `GoldMined`, `MoldGrown`); each player record snapshots them as `Seen*` on every `hello`. On reconnect the server sends a `{type:"recap", ticks, blocks, gold, mold}` message with the deltas since that player was last seen, then advances the snapshot (deltas are clamped at zero so a post-reset stale snapshot never goes negative; `resetWorld` also scrubs `Seen*`). The client only shows the `#recap` toast when `ticks >= 120` (>= 60s of absence) AND at least one of blocks/gold/mold is non-zero, so reconnect floods never stack a toast. The toast reads "While you were away (Nm): X blocks mined, Y gold mined, Z tunnels molded over", auto-hides on a wall-clock timer (ticks cannot reset the fade), and dismisses on click. To exercise it: connect once (sets the baseline), close the page, `POST /api/advance?ticks=5000`, reopen with the SAME browser profile/localStorage token; the toast appears. Reload again immediately and it does not (the snapshot just advanced, under the 120-tick floor). A death-respawn carries the old `Seen*` forward so dying fakes no recap.

## Gotchas

- Mining is deliberately slow (one plain-rock cell takes ~4 real hours at 1x; a tunnel is a day-scale project), but dwarves WALK fast (`cells_per_second = 1.0`, one cell per two ticks). Use `POST /api/advance?ticks=N` to fast-forward long waits; connected clients receive a fresh snapshot afterwards.
- `data/terrain.toml` colors are authoritative for terrain, `data/entities.toml` for entities and structures; update the color list above if either changes.
- Mining is AOE: a mining dwarf damages EVERY adjacent lit mineable face each tick at full mine_damage, so several progress bars fill at once around one miner and gold events can arrive in bursts. Chips pay only for the TARGET face; swept neighbors get debris and progress bars but no numbers.
- Mining is integer damage against terrain hit points: the ws snapshot `mining` map carries int damage per cell, and the bar fraction is damage / the terrain's `hitPoints` from `terrainTypes` (rock 28800, soft rock 7200 in `data/terrain.toml`). Dwarf `mine_damage` (1 per tick) lives in `data/entities.toml`.
- Floating numbers are GOLD ONLY (`#ffd75e`, 9px, ~1s lifetime: 400ms rise then 600ms fade): the coalesced chip "+N" per struck face per tick message. There are no separate damage numbers anymore — damage progress reads from the mining bar and the break pace.
- Golden strikes: each mining swing rolls `World.CritChance()` (`crit_chance` in `data/sim.toml`, base 0.02, plus luck claims); a crit multiplies every chip that swing pays by `crit_mult` (10), fires a "gold" event with the crit's total as `amount`, feeds `GoldStrikes`/g24 chatter, and pops the gold particle burst client-side. There is NO block-break gold roll anymore (`gold_chance`/`gold_min`/`gold_max` are gone); breaks always emit "mined". Placing a torch spends 1 colony gold.
- Chip gold: DAMAGE IS GOLD. Every point of damage a face absorbs pays that terrain's `chip_gold` (per-terrain multiplier, currently 1 for rock/soft_rock/mold) straight to colony gold and `GoldMined`, immediately — so income per swing = damage per swing, damage upgrades and AOE weapons raise income directly, and a block pays exactly `hit_points * chip_gold` over its life (overkill past the break pays nothing). EVERY damaged cell pays, including splash-damaged neighbors, each emitting its own `"chip"` event (`amount` = gold, `x`/`y` = the struck face) on the ws tick stream; the client coalesces chips per face per tick message into a gold `+N` float and keeps them out of the `#events` feed. Ordinary chips never enter `GoldStrikes`/g24 chatter — golden-strike crits do (see the crit gotcha below). E2e signature of a dig: colony gold rising by the tunnel's total hit points rather than in rare lumps.
- Thought bubbles over dwarves are intermittent by design: visible ~3s out of every 60s per dwarf (phase-offset by entity id). A missing bubble is usually just the cadence window; sample for at least 60s or check the entity's soc/g24/action via the API instead. Thought copy and conditions live in the `thoughts` list in `data/entities.toml`.
- Entity tick data arrives over `/ws`; confirm liveness by counting websocket frames or watching `#events` tick numbers, not by expecting positions to change.
- `/favicon.ico` 404s in the console; pre-existing, ignore.
- "64x" yields only a few ticks/sec observed client-side, not 128/s; don't treat slow ticks as breakage.
